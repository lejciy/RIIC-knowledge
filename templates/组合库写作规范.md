# 组合库写作规范

> 适用范围：`docs/3-组合库/` 全部内容。目标：结构化知识，服务 RAG 向量检索与知识图谱构建。深稿骨架见 [tpl-体系论证.md](tpl-体系论证.md)。本文是维护者规范，不入 RAG 语料。

## 一、内容分层与真源

| 层 | 位置 | 定义 |
|---|---|---|
| 跨设施体系 | `跨设施体系/` | 去掉中枢或跨设施资源（发电、办公室、基建内计数等）后组合即不成立 |
| 单站组合 | `单站组合/` | 站内自成一格，无跨设施依赖 |
| 效率散件 | `高效率散件.md` | 无指定队友依赖的填位干员；散件效率表与筛选口径合一 |

真源与引用方向：

- 单组合知识的唯一真源 = 该组合深稿（正文 + front matter）。
- `组合注册表.md` = 全库词表 + 组合定义总表；总表由脚本从深稿 front matter 渲染，渲染脚本落成前人工同步，落成后请勿手改。
- `README.md`、`组合总览.md` = 纯目录（规范名＋一句话＋链接），由脚本渲染，不复述知识。设施向汇总页已撤销（2026-09-14，比照 `跨设施组合.md` 先例），设施向导航由组合总览的设施列承载。
- 引用单向：目录层 → 深稿 → `2-干员技能/` 快照与释义；禁止反向引用，禁止跨层复述成员表或效率数值。
- 消歧三页：`歧义-子串对`（自动）、`歧义-简称合称`（人工）、`歧义-组合别名`（自动，汇聚自深稿 `aliases`）。

## 二、front matter 规格

深稿 front matter 是图谱的直接数据源，字段与词表如下：

```yaml
---
type: combination            # 固定值
status: canonical            # canonical | draft | needs_review
updated: 2026-09-11
source: [公孙长乐]            # 数值与结论的来源
system_id: witch_long_beta   # 稳定英文 id
name: 龙舌兰组                # 规范名，与正文 H1 一致
aliases: [巫恋组]             # 别名：社区俗称、指向本组合的合称
layer: 单站                   # 单站 | 跨设施
product: [贸易, 赤金]         # 产物词表（可多值）
facilities: [贸易站]          # 占用设施
members:                     # 成员与层级
  - name: 巫恋
    tier: 核心
    promotion: 精2
  - name: 卡夫卡
    tier: 重要
    promotion: 精2
    note: 裁缝β四选一         # 可选：分支、选择规则
conflicts:                   # 互斥（类型见第五节）
  - with: 可露希尔特别订单
    type: 同站
    reason: 订单被改写为特别订单，龙舌兰的投资不再生效
coexists_with: [但书]         # 明确可同布局共存的组合
---
```

词表（闭合，不得自造值）：

| 字段 | 取值 |
|---|---|
| `status` | `canonical` 定稿 / `draft` 草稿 / `needs_review` 数值或结论存疑 |
| `layer` | `单站` / `跨设施` |
| `product` | `贸易`、`赤金`、`经验`、`通用制造`、`搓玉`、`非生产` |
| `tier` | `核心` / `重要` / `次级` / `挂件`（含义见组合注册表） |
| `promotion` | `精0` / `精1` / `精2` / `无要求` |
| `conflicts[].type` | `同站` / `同设施` / `资源竞争` |

## 三、正文章节骨架

每个深稿正文从下列二级标题中按需取用、顺序不得调换；不设本骨架之外的二级标题，确需细分时用三级标题：

| 节 | 承载内容 |
|---|---|
| `## 一句话结论` | 规范名＋别名＋产物＋满配锚点，100 字内；首句点别名（如「又称巫恋组」） |
| `## 启用条件` | 硬性门槛：干员、练度、设施等级、布局、班次；含「不满足时不开」的判定 |
| `## 建议用法` | 谁进哪个设施、第三人选择、站位与班次约束、机制依据、特殊用法 |
| `## 成员与档位` | 成员表（层级/练度/作用）＋效率分档表；分支选择规则写明 |
| `## 缺人降级` | 逐档降级路径，每档标明损失 |
| `## 互斥与共存` | 与 front matter `conflicts`/`coexists_with` 一一对应，展开原因与共存布局 |
| `## 数值锚点` | 可验证数字，每条带来源与口径；只标定效率，效率到产出的折算不在本页体现，产出折算与基准归 [[产出常数表]] |
| `## 边界与误区` | 常见误读的正面澄清、组合值与散件值的区分、「不是固定组合」类社区流传纠错 |

行文第一约束是**语料干净、不同义反复**（取节要求与 `tpl-特殊技能释义.md` 同源）：

- 同一信息只在一处展开：某节只剩对其余节内容的复述或换一种说法的重述时，整节删除、增量信息并入其余节——如降级路径已由「启用条件」的练度判定与「成员与档位」的分档表承载时，删「缺人降级」节。
- 节内容为空时直接删节，不保留标题写「无××」占位；「无同站互斥」类否定信息由 front matter 的空 `conflicts` 表达。
- 正文不原样复述 front matter 的结构化字段；「互斥与共存」只写展开后的原因与布局。
- 不复述机制真源页（模块1/模块2）已写明的内容，只链接。

单站与跨设施深稿共用本骨架，差异只在「建议用法」「成员与档位」内是否按设施分组。

## 四、别名规则

- 别名唯一真源 = 深稿 front matter `aliases`；注册表总表、`歧义-组合别名.md` 均为渲染产物。
- 收录口径：社区俗称（巫恋组→龙舌兰组）、指向本组合的干员合称。只收有据可查的叫法，不得编造；历史规范名（旧称）不收录，直接清除。
- 别名须同时出现在正文首段（「又称××」），保证分块向量化后口语提问可召回；别名不单独成节——量少单薄，单独成节降低块的信息密度。带消歧需求的别名（同一俗称指向多个对象）在「边界与误区」节展开（如格拉斯哥帮组的「推王」）。
- 干员名歧义（推王指谁）归 `歧义/`，与组合别名分页处理；组合别名页只做一意映射，撞名时按设施线索消歧并标注。
- 语料中禁止出现「旧称××不再使用」「不得沿用××」句式：旧称要么作为别名收录，要么彻底清除。

## 五、互斥建模

| type | 语义 | 判定 |
|---|---|---|
| `同站` | 同一设施房间内不能同放 | 但书×可露希尔、深海猎人组×槐琥 |
| `同设施` | 严格不能在相同设施内同时上班（跨房间机制排斥） | 承曦格雷伊「晨曦」×驻发电站的小车体系（阿兰娜＋温米、布丁等，见自动化组） |
| `资源竞争` | 共享有限资源，可挤占但非硬互斥 | 共同核心只能进驻一座设施（蕾缪安：能天使组×拉特兰） |

front matter `conflicts` 与正文「互斥与共存」节一一对应；`组合总览` 的互斥章由两者渲染。

通则型互斥的登记约束：

- 可由通用机制推导的互斥不做逐组合展开。当前通则两条：
  - 归零类：自动化·α/β、仿生海龙、科学改造/流程优化清空同站其他干员提供的常规生产力——凡进驻制造站、以常规生产力技能输出的组合一律同站互斥。机制层真源在 `2-干员技能/释义/自动化.md`（清零范围、豁免、可同站队友），组合层总述在自动化组深稿「互斥与共存」。
  - 特殊订单改写类：改写层（佩佩＞可露希尔＞U-Official）覆盖被覆盖层（但书违约订单、龙舌兰投资订单）——任一改写者与但书、龙舌兰同站即互斥，改写者之间同站按优先级取一、其余空转，均须分站带队。机制层真源在 `1-基础设定/设施与进驻/贸易站机制.md`·特殊订单（优先级全表），组合层总述在但书深稿「互斥与共存」。
- 通则登记方式：组合层总述只出现在自动化组、但书两篇深稿；其余深稿至多一行指针式登记——归零类为 front matter `conflicts` 一条边（对向自动化组）＋正文一行「同站互斥（归零通则，见××）」，改写类对向是干员而非组合、front matter 不登记，只留正文一行指针；指针行可带最小必要事实（如「佩佩优先级在可露希尔之上」），不复述机制全文。
- `组合总览` 互斥章对通则边不逐组合渲染，只保留通则行；组合对组合的实例边（但书×可露希尔特别订单、龙舌兰组×可露希尔特别订单等）照常双向登记，通则不替代实例边。

「互斥与共存」的收录口径：

- 只登记带约束增量的关系：`conflicts` 的展开、真实的站位/资源约束（挂件位竞争、同站分工机制、站外终端豁免等）。
- 普适型资源竞争不逐组合登记：对整类组合成立的竞争（所有中枢组合共享 5 人位、所有办公室组合共享席位、计数体系共享挂件位）由 `组合总览` 互斥章的全局条目统一承载，深稿不写 per-combo 边；只有竞争特异到改变成形判断（共同核心只能进驻一座设施、两组合抢同名设施位致其一无法成形）才登记 `资源竞争`。
- 「不冲突」「互不干扰」「完全互补」类无约束表述不写；`coexists_with` 只收机制层绑定的共存——共享成员、互相改变机制判定的同站用法（订单类型分工、归零无损入位、技能互为计数对象等），「不同设施各干各的」是默认状态。「订单类型改造者与任意纯效率班底互不干扰」「第三席可上任意纯效率角色」类正交关系是通用属性，正文一句通用语言表达、可带例名，不做组合名穷举登记。「无同站互斥」类否定信息由空 `conflicts` 表达，通则已覆盖的不重复登记。
- 存量超收（普适型资源竞争边、默认共存枚举）已全库清除，新登记按本口径执行。

## 六、语料洁净与 RAG 分块要求

- 按 `##` 二级标题分块，**每块自包含**：块内写明组合名，不依赖上文指代（「缺伺夜时叙拉古组…」，禁止裸写「缺伺夜」）。
- 无维护痕迹：不写 TODO、待复核、待确认、待按××复核、内部裁决编号（C2/T7 等）、日期化规则、「请勿手改」类注释。
- 无产品策略：展示开关、推荐名额、报告措辞、前端门闩不进模块3（练卡推荐产品侧文档已于 2026-09-14 移出本库，随 ArknightsInfraCalc 项目维护）。
- 无否定式旧称残留（见第四节）。
- 数值必须带来源与口径；无来源或存疑的数值，文档 `status` 置 `needs_review`，不得带「待核实」字样入正文。
- 技能运作原理引用 `2-干员技能/` 释义，不复制原文。

## 七、渲染与校验

- 渲染：注册表总表、组合总览、组合别名页由 `scripts/` 下 mjs 脚本从深稿 front matter 生成，头部标注生成注释。
- 校验脚本至少检查：front matter 词表闭合、`members`/`conflicts` 与正文表格一致、`aliases` 全库无冲突、目录页链接有效、正文无禁用句式（旧称否定式、待复核类）。

## 八、与产品侧的边界

练卡推荐、排班求解等下游产品的消费策略（收集建议触发条件、多身份优先、展示开关、输出口径）不在本库维护——练卡推荐文档已于 2026-09-14 处置：知识本体由模块3/模块6 承载，产品侧文档移出本库（本地备份于 ArknightsInfraCalc 项目 `docs/练卡推荐归档/`）。两边冲突时，先修知识本体，产品侧跟随。
